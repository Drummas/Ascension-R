# NVIDIA DLSS, step 1: Super Resolution and DLAA (2026-11-23)

`graphics.scaling = dlss` has DLSS Super Resolution rebuild scene frames in AMD FSR's place, on NVIDIA RTX cards. This
PC has an AMD card, so DLSS itself has not run here: what was checked is the build, the download, the launcher and every
path that falls back to FSR. RTX owners among the reporters were asked to try it (issue #39).

## How it is put together

- **The SDK.** NVIDIA's NGX SDK from the DLSS SDK 310.9.16 (github.com/NVIDIA/DLSS, tag commit 9981c63): six headers and
  `nvsdk_ngx_d.lib`, the static library for the DLL C runtime (/MD) this build uses, which finds the driver's NGX. They
  are NVIDIA's (`LicenseRef-NvidiaProprietary`), so `ps3recomp/CMakeLists.txt` (`PS3RECOMP_DLSS`, which the port's
  `PORT_DLSS` turns on) fetches them into the build folder, each checked by its SHA-256, and builds without DLSS when it
  cannot. The Kit's DLL never sees them: they are in the exe only.
- **The DLL.** `nvngx_dlss.dll`, NVIDIA's signed release build (59 MB), is not shipped. The launcher downloads it from the
  same commit on NVIDIA's GitHub when the player picks NVIDIA DLSS and says yes (`port/dlss_get.cpp`, `--dlss-get`),
  checks its size, SHA-256 and that NVIDIA Corporation signed it, and puts it in `dlss\` beside the exe. NGX checks
  NVIDIA's signature again when it loads it.
- **The steps** (`ps3recomp/libs/video/rsx_dlss.cpp`) are those of NVIDIA's DLSS Programming Guide: NGX with a project
  id of the port's own (a CUSTOM engine, 5.2.1), the capability parameters (is DLSS there, is the driver new enough),
  each mode's optimal render size and range for the display (5.2.8), the feature created at its mode's optimal size on
  the frame's command list, one evaluate a frame with the render size as the subrect (3.2.2).
- **The inputs** are FSR's, from `rsx_fsr3_prepare`, now made without FSR's contexts as well
  (`rsx_fsr3_inputs_create`, `rsx_fsr3_inputs_get`): the scene after the title's tone mapping, 8 bits in sRGB, which is
  DLSS's LDR mode (IsHDR 0, 3.1.2); depth as R32_FLOAT with the near plane at 0; motion at the render's size in UV units
  from a pixel to where it was, without the jitter (MVLowRes, the motion scale the render size, 3.6); auto exposure.
  The inputs go to NON_PIXEL_SHADER_RESOURCE for the evaluate and back (3.4). The texture LOD bias is FSR's,
  log2(render / display) - 1, the guide's formula (3.5).
- **The jitter** is Halton (2, 3) over 8 x scale^2 phases, the guide's pattern and count (3.7.1), applied to the projection
  as FSR's is and given to DLSS in render pixels with y down.
- **The mode** is the one, of DLAA, Quality, Balanced, Performance and Ultra Performance, whose range takes the render
  size and whose own scale is nearest the render's against the window. The Internal resolution sets the render size, so
  it is not a row of its own. **DLSS preset** (`graphics.dlss_preset`) asks every mode for J, K, L or M, or leaves each
  its own (`auto`).
- **Falling back.** Not an NVIDIA card, NGX not in the driver, a driver too old, no DLL, no mode for the sizes, a feature
  that does not start or three failed evaluates in a row: the log says which, and FSR 3's upscaler takes over, as for a
  player who picked it. MLAA's frame order goes as with FSR (`main.cpp` switches `mlaa_path_off` on for `dlss` too).

## Checked on this PC

i5-12400F, RX 6700 XT, a 1080p display; the build with clang-cl and NVIDIA's library linked; one run each.

- `--dlss-get`: 56.2 MB in 25.1 s over 4 connections; SHA-256 d00b5b0a..., signed by NVIDIA Corporation, version
  310.9.16.0; in `dlss\`.
- The fight replay with `graphics.scaling = dlss`, 1080p internal: `graphics.scaling = dlss: not an NVIDIA GPU; FSR 3`,
  then FSR 4.1.2 at 1080p from 1080p, MLAA's path off, the picture as with FSR.
- The same with `D3D12_DLSS_ANY_GPU=1`, which asks NGX on any card: NVIDIA's loader logged through the port's callback
  (`[ngx] ... failed to locate NGX core path via registry key`), `NGX did not start (feature not supported)`, then FSR 3
  as above, no crash.
- The launcher with DLSS picked on this card: `DLSS needs an RTX card: AMD FSR instead` on the ready check.

## What a tester looks at

- The log: `[dlss] NGX up, DLSS available`, each mode's sizes, then
  `[dlss] DLSS 310.9.16 Quality: 2560x1440 from 1920x1080 (made at ...), preset ..., N jitter phases, N MB` and
  `[D3D12] upscaler on: ...`. A `graphics.scaling = dlss: ...; FSR 3` or `[D3D12] DLSS: ...; FSR 3` line says why not.
- NVIDIA's own indicator: the DWORD `ShowDlssIndicator` = 1024 under
  `HKEY_LOCAL_MACHINE\SOFTWARE\NVIDIA Corporation\Global\NGXCore` shows DLSS's version and sizes on screen with the
  release DLL (the guide's 3.18); 0 or deleting it turns it off.
- The picture against AMD FSR at the same spot, the same internal resolution: still scenes shaking or blurring point at
  the jitter (`D3D12_DLSS_JITTER=1,-1`, `-1,1` or `-1,-1` to try); things that move smearing or leaving trails, at the
  motion (`D3D12_DLSS_MV=...`). The guide's other levers are in its SDK's development DLL, which may not be passed on.
- Frame rate and GPU time against FSR, and the VRAM line on 8 GB cards.
- Linux: Proton has to present the card as NVIDIA's with its NVAPI (`PROTON_ENABLE_NVAPI=1` where it is not the
  default) for DLSS to be offered.

## Not done

- DLSS on an RTX card: everything above is waiting for the testers.
- DLSS Frame Generation: only through Streamline (NVIDIA's DLSS-G guide), with Reflex and its own swap chain handling;
  hosting `nvngx_dlssg.dll` directly would take NVIDIA's internal interface apart, which its license does not allow.
- Sharpening after DLSS: FSR's RCAS is not used with it.
